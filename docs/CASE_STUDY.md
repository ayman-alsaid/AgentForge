# AgentForge — Technical Case Study

## The problem: recurring reasoning cost

A tool-using AI agent often pays full reasoning cost every time it performs a workflow, even when the workflow is structurally identical to one it has already completed successfully.

That is economically wasteful and architecturally unnecessary.

AgentForge was designed around a different premise:

> **A successful agent run should become reusable execution infrastructure.**

The goal is not to cache a text answer. It is to capture the *shape* of a successful tool-use trace, abstract the truly variable parts, and replay the known structure at the lowest possible reasoning cost.

---

## What the system is

AgentForge is a full-stack tool-calling agent execution platform with five connected layers:

1. **ReAct execution** — run tool-using agents with persisted multi-turn state.
2. **Trace capture** — record actual tool calls, arguments, results, errors, and durations.
3. **Skill abstraction** — turn the successful trace into a parameterized recipe plus `variables_schema`.
4. **Replay** — deterministic where possible, guided cheapest-first resolution where not.
5. **Packaging** — publish a verified Skill as a customer-facing product without exposing its internal trace.

The same ToolRegistry supports both local tools and remote MCP tools.

---

# The engineering problem

The naive version is “store the result and reuse it.”

That fails as soon as the next request changes.

A more realistic workflow looks like:

```text
search for X
→ inspect the new search result set
→ choose an official source
→ read it
→ produce the answer
```

A new value of `X` creates new search results. The URL consumed by the next step cannot be known before runtime.

This creates three categories of trace data:

- **true caller inputs** — values that should become variables;
- **deterministic values** — known from the recorded recipe or current inputs;
- **runtime-derived values** — values that only exist after a prior step executes.

AgentForge's core engineering problem is deciding which category a value belongs to and resolving it without quietly falling back to full reasoning.

---

# Design goals

## 1. Zero reasoning cost where replay is genuinely deterministic

If the workflow does not need fresh judgment, no LLM call should be inserted simply because the platform is “AI-powered.”

## 2. Cheapest-first resolution when a chain is dynamic

A runtime dependency should not automatically trigger a complete ReAct loop.

## 3. Conservative abstraction

More variables are not automatically better. Exposing intermediate results as caller inputs creates fragile workflows.

## 4. Verifiable resolution

When a model is allowed to choose among runtime candidates, it should not be allowed to invent candidates that never existed.

## 5. Commercial packaging without implementation leakage

The customer should receive a product contract, not the internal recipe.

# Architecture

```text
user request
    │
    ▼
ReAct executor ───────────────► ToolRegistry ─────► local / MCP tools
    │
    ├── persist conversation + tool results
    │
    ▼
execution trace
    │
    ▼
abstractor
    │
    ├── concrete inputs → {{variables}}
    └── runtime-derived values remain protected
    │
    ▼
Skill
    │
    ├── deterministic replay
    │
    └── guided replay
           │
           ├── user input
           ├── heuristic extraction
           ├── narrowly-scoped LLM rescue
           └── recorded default
```

---

# Decision 1 — tiered resolution instead of full-agent fallback

### Alternative considered

Whenever a replay step depends on a value produced at runtime, hand control back to the full agent.

### Why that was rejected

It would make the difficult workflows — the ones with chained steps — economically equivalent to fresh agent runs.

The product would still work, but the project's economic thesis would collapse.

### Chosen design

Resolve the value through a strict cheapest-first sequence:

1. caller-provided value;
2. deterministic/heuristic extraction from prior results;
3. tiny model rescue for that one value;
4. recorded default.

### Trade-off

More state, more execution paths, more tests, and more observability requirements.

The complexity is accepted because it preserves the difference between **fresh reasoning** and **reusable execution**.

---

# Decision 2 — conservative abstraction

The abstractor does not blindly template every concrete value it sees.

URLs are skipped by default because they are frequently generated by a previous step.

### Why this matters

Imagine the original run:

```text
search("FastAPI release")
→ https://fastapi.tiangolo.com/...
→ read_url(that result)
```

If the URL is exposed as a user variable, a future caller can provide a URL inconsistent with the new search input. The Skill appears more configurable but becomes less reliable.

AgentForge therefore optimizes for **meaningful variables**, not maximum parameter count.

---

# Decision 3 — smart URL selection before AI rescue

For search-result chains, AgentForge attempts to identify the most likely official/relevant URL using deterministic scoring before spending tokens.

Signals include documented positive weights for terms such as `docs`, `documentation`, `official`, and `github`, plus TLD/query-match signals and penalties for lower-quality patterns.

Only close rankings escalate.

This is important because it reframes AI as an ambiguity resolver, not the default control system.

---

# Decision 4 — anti-hallucination candidate validation

If an LLM rescue is needed, the returned value must correspond to a value that actually exists in the candidate list.

The model is allowed to **select**, not **invent**.

This converts an open-ended generation problem into constrained choice.

---

# Decision 5 — one ToolRegistry for local and MCP tools

The executor does not care where a tool lives.

A local tool and a remote MCP tool both satisfy the same `BaseTool` contract.

MCP tools are wrapped and namespaced:

```text
mcp__{server}__{tool}
```

This prevents collisions and keeps the ReAct executor unchanged as integrations grow.

### Trade-off

Protocol translation complexity moves into the adapter layer, but that is preferable to duplicating execution semantics across the platform.

---

# Decision 6 — HTTP/SSE MCP only

Stdio support is deliberately absent.

For a shared deployment, stdio means spawning arbitrary subprocesses. AgentForge chooses the smaller attack surface of HTTP/SSE.

This is not an implementation omission being disguised as philosophy; it is a deliberate deployment boundary documented by the project.

---

# Decision 7 — marketplace information hiding at the API layer

A frontend-only concealment of `execution_trace` would not protect the implementation. A customer could simply inspect the API response.

Therefore customer-facing marketplace routes are designed to omit internal traces and tool arguments.

The customer receives:

- product name;
- description;
- price;
- generated input form;
- execution result.

The mechanism remains owner-side.

---

# Frontend as observability

AgentForge's frontend turns the cost model into visible product behavior:

- ToolCallCards expose tool state and duration;
- replay mode is explicit;
- deterministic replay shows a zero-token reasoning banner;
- guided replay shows per-step strategy chips;
- rescue calls and guidance-token counts are visible;
- MCP tools are inspectable through namespaced entries;
- customer execution hides internal traces by design.

This is an important engineering choice: optimization should be inspectable by an operator, not hidden in backend logs.

# Verification

The project source documents six explicit verification scripts:

- `test_engine.py`
- `test_real_engine.py`
- `test_recipe_skill.py`
- `test_guided_skill.py`
- `test_dual_flow.py`
- `test_mcp_integration.py`

The strongest evidence paths are:

### Deterministic replay

`test_recipe_skill.py` verifies record → abstraction → replay with a changed topic while the deterministic replay itself uses no LLM tokens.

### Guided chained replay

`test_guided_skill.py` verifies that a search/read chain can resolve to the correct official documentation through the heuristic path without rescue-token use in that run.

### MCP lifecycle

`test_mcp_integration.py` verifies connect → discover → register → call through the normal registry → unregister.

### Outcome correctness over “did not crash”

The project's review history explicitly records a lesson from a vacuously green test: absence of exceptions does not prove the output was correct.

Later tests assert content-level outcomes such as ensuring a replay switched from the original topic to the new topic.

# What I built vs what I used

External systems provide model access and search.

The engineering contribution is the control architecture around them:

- ReAct executor;
- persistent tool history;
- trace recorder;
- abstraction logic;
- deterministic replay;
- guided resolution;
- smart URL selection;
- candidate validation;
- MCP integration;
- packaging contract;
- cost observability.

The system's value is not “an LLM can call tools.”

It is:

> **a successful reasoning path can become a lower-cost executable asset.**

# Limitations

## Longer dependency chains

The documented implementation is strongest for short chains such as search → choose URL → read. Longer chains create compounded dependency resolution and need more generalized planning/dataflow semantics.

## MCP restart lifecycle

Live MCP clients are tracked in memory. Restart recovery remains a lifecycle-hardening area documented by the source project.

## Staleness

A recorded workflow can become stale if external tool behavior, page structures, policies, or APIs change.

Replay reduces reasoning cost; it does not remove the need for monitoring and re-recording.

## “Zero token” boundary

Zero-token replay refers specifically to LLM calls in the deterministic replay path. External tools can still have infrastructure or API costs.

---

# Generalization

The reusable architecture is:

```text
capture a successful process
→ abstract real variables
→ resolve runtime ambiguity cheapest-first
→ replay the repeatable parts deterministically
→ expose only the result contract
```

This maps naturally to repeatable workflows in RPA, incident-response runbooks, support automation, sales research, and competitive intelligence.

But domain adaptation still requires domain-specific tools, heuristics, and freshness rules.

And there are workflows where replay is the wrong optimization entirely — especially when the value comes from fresh creative judgment.

---

# Conclusion

AgentForge treats agent economics as an engineering problem rather than a pricing afterthought.

Its core proposition is simple:

**pay full reasoning cost when reasoning is novel; preserve successful reasoning as executable structure when it is not.**

That required more than caching. It required trace semantics, conservative abstraction, runtime dependency resolution, constrained model rescue, information boundaries, and operator-visible cost behavior.

That architecture — not the presence of an LLM — is the project.
